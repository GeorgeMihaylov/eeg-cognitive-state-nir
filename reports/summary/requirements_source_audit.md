# Аудит источников требований

## Результат

Официальный файл технического задания или утверждённый план работ в tracked-дереве
и доступной Git-истории не найден. Поэтому карта покрытия не называется
соответствием официальному ТЗ: её основной источник классифицирован как
`project_plan`, а не `technical_specification`.

Основным доступным источником выбран `README.md`, разделы «Назначение проекта»,
«Данные» и «Архитектура экспериментального стенда». README формулирует цель
единого воспроизводимого benchmark, требования к сопоставимым splits,
предотвращению subject/logical-record leakage, поддержке нескольких
представлений данных и сохранению воспроизводимых артефактов. Он не задаёт
полный договорной scope, обязательность каждого внешнего датасета,
приёмочные пороги и приоритеты всех deliverables.

## Проверенный охват

Проверены tracked-файлы по маскам:

```text
README*
docs/**
reports/**
*.md
*.docx
*.pdf
*.txt
*.yaml
*.yml
```

Также проверены Git history, текущие registries, experiment/config summaries,
`AGENTS.md` и `PROJECT_CONTEXT.md`. Каталога `docs/`, tracked DOCX/PDF и файла,
явно обозначенного как техническое задание, нет. Поиск выполнялся по словам
«техническое задание», «ТЗ», «цель проекта», «задачи проекта»,
«требования», «ожидаемые результаты», «критерии», «персонализация»,
«адаптация», «предобработка», «признаки», «потоковая обработка»,
«мультимодальность» и «демонстрационный интерфейс».

Использованные команды аудита:

```powershell
git ls-files
git log --all --name-only -- "*.docx" "*.pdf" "*.md" "*.txt" "*.yaml" "*.yml"
rg -n -i "<поисковые формулировки>" README.md reports AGENTS.md PROJECT_CONTEXT.md
git log --all --oneline -- bench experiments reports README.md
```

`benchmark_results/` не использован как источник формулировок требований.
Runtime artifacts используются только через уже курированные experiment
records и tracked summaries как evidence выполнения.

## Иерархия источников

1. `README.md` — основной доступный `project_plan`.
2. Tracked experiment reports, `reports/summary/experiment_registry.yaml` и
   связанные configs — evidence реализации, воспроизводимости и результатов,
   но не источник обязательности.
3. Git history — evidence происхождения отдельных возможностей и решений.
4. `AGENTS.md` и `PROJECT_CONTEXT.md` — внутренние планы и ограничения
   выполнения; они не подменяют официальный текст ТЗ.

Незакоммиченные материалы текущего рабочего дерева из этапа аудита конфигов
использованы генератором как входные registries по явному заданию задачи, но
не используются как самостоятельное доказательство закрытия требований.

## Существенные неоднозначности

- Не определено, какие внешние наборы данных обязательны. WESAD имеет loader и
  task, но не имеет подтверждённого полного experiment contract в текущем
  реестре; STEW встречается только как возможное направление.
- Не установлено, требуется ли мультимодальность как объединение EEG с
  независимой модальностью в одном эксперименте. Multi-output PM regression
  не считается мультимодальностью.
- Не найден утверждённый источник численного критерия персонализации
  `accuracy >= 0.75`. Карта сохраняет его как отдельный проверяемый критерий
  с неустановленной нормативной силой и честно фиксирует фактический максимум
  `0.6349206349`.
- Streaming replay и demo входят в внутренний план завершения платформы, но
  не подтверждены как обязательные пункты официального ТЗ.
- README отстаёт от фактического состояния PM regression и части завершённых
  экспериментов, поэтому он пригоден как источник цели, но не как единственный
  источник статуса реализации.

## Что требуется добавить позднее

Для окончательной приёмочной трассируемости нужен официальный документ ТЗ или
утверждённый план работ с:

- стабильными идентификаторами требований;
- обязательностью и приоритетом каждого пункта;
- точным scope наборов данных и модальностей;
- численными критериями качества и способом их агрегации;
- обязательными deliverables, streaming/demo сценариями;
- правилами приёмки и допустимыми исключениями.

После появления такого документа ручной реестр следует сопоставить с ним,
сохранив текущие evidence и отдельно отмечая изменившиеся или исключённые
проектные обязательства.
